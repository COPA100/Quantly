# Quantly infrastructure

Terraform for the whole AWS stack. Nothing here is created through the console.

The stack is built to be **stood up for a demo and torn down afterwards**, not run 24/7. Day-to-day development happens on `docker compose` for $0. See the [cost notes](#cost) for why.

## What it provisions

```
                    internet
                       │
                 ┌─────▼─────┐
                 │    ALB    │  80 (443 with a certificate)
                 └─────┬─────┘
                       │ :8000
   ┌───────────────────▼───────────────────┐
   │ ECS cluster                           │
   │  api    (Fargate,      0.25 vCPU)     │
   │  worker (Fargate Spot, 1 vCPU)        │
   └───────┬───────────┬───────────┬───────┘
           │           │           │
      ┌────▼───┐  ┌────▼────┐  ┌───▼──┐
      │  RDS   │  │  Redis  │  │  S3  │
      └────────┘  └─────────┘  └──────┘
```

| Piece | Where | Notes |
|---|---|---|
| VPC, 2 public subnets, security groups | `modules/network` | No NAT gateway. Tasks get a public IP for outbound, inbound is locked down per tier. |
| S3 bucket for raw CSVs | `modules/s3` | Private, encrypted, uploads expire after 90 days. |
| RDS Postgres 16 | `modules/rds` | `db.t4g.micro`, single-AZ, no public IP. |
| ElastiCache Redis | `modules/redis` | `cache.t4g.micro`, single node. Celery broker + price cache. |
| ECR repositories | `modules/ecr` | One each for the api and worker images, last 5 images kept. |
| Fargate service | `modules/ecs-service` | Reusable. Task definition, service, IAM roles and log group. Instantiated twice in `ecs.tf`. |
| ECS cluster, secrets, the two services | `ecs.tf` | |
| Application load balancer | `alb.tf` | In front of the api only. The worker has no inbound at all. |
| Task role policies | `iam.tf` | What each service's code may call. |
| Budget alarm | `budget/` | Separate root with its own state, see step 0. |
| State bucket, GitHub OIDC roles | `ci/` | Separate root with its own state, see step 0. What [CI/CD](#cicd) runs as. |

### Security model

- **Network:** only the ALB is reachable from the internet. The api accepts traffic only from the ALB, RDS and Redis only from the api and worker, and the worker accepts nothing.
- **IAM:** each service has its own execution role and task role. The execution role can pull only that service's image, read only that service's secrets, and write only to that service's log group. The api task role can `s3:PutObject` into the bucket, the worker can `s3:GetObject` from it, and that is all either can do.
- **Secrets:** the database password and JWT secret are generated by Terraform, stored as SSM `SecureString` parameters, and injected by ECS at task start. They are never in a tfvars file or a task definition. They *are* in the Terraform state, so treat the state as a secret. It lives in a private, encrypted bucket and never in git.

## Prerequisites

- Terraform >= 1.10
- AWS CLI v2, authenticated against the target account (`aws sts get-caller-identity` should work)
- Docker, to build and push the images

State for the main stack is remote, in the S3 bucket that `ci/` creates, so a laptop and GitHub Actions always work against the same stack. Locking uses S3's native lockfile, there is no DynamoDB table. The two small roots that have to outlive the stack (`budget/` and `ci/`) keep local state: they are applied once by hand and never destroyed.

## Runbook

All commands run from `infra/` unless noted. They are written for bash (Git Bash works on Windows).

### 0. Once per account: budget alarm, state bucket, CI roles

Set the budget alarm **before** creating anything else. It is the safety net for a forgotten teardown.

```bash
cd budget
terraform init
terraform apply -var alert_email=you@example.com   # default limit is $20/month
cd ..
```

It emails at 50% actual, 100% forecasted and 100% actual spend. Leave it in place permanently. It is deliberately not part of the main stack, so `terraform destroy` there never removes it.

Then create the state bucket and the roles GitHub Actions assumes:

```bash
cd ci
terraform init
terraform apply   # -var github_repository=owner/name on a fork
cd ..
```

An AWS account can only hold one GitHub OIDC provider. If yours already has one, import it first with `terraform import aws_iam_openid_connect_provider.github <arn>`.

Both cost nothing to leave in place (a versioned bucket holding one small file, and a few IAM resources). The outputs feed step 1 and the [CI/CD](#cicd) setup.

### 1. Init

```bash
terraform init \
  -backend-config="bucket=$(terraform -chdir=ci output -raw state_bucket)" \
  -backend-config="key=dev.tfstate" \
  -backend-config="region=us-east-1"
```

The key is per environment, so `prod.tfstate` would be a second, independent stack.

### 2. Create the image repositories

The services cannot start until their images exist, so the repositories go up first.

```bash
terraform apply -var-file=environments/dev.tfvars -target=module.ecr
```

### 3. Build and push the images

```bash
REGION=us-east-1
API_REPO=$(terraform output -json ecr_repository_urls | jq -r .api)
WORKER_REPO=$(terraform output -json ecr_repository_urls | jq -r .worker)

aws ecr get-login-password --region $REGION \
  | docker login --username AWS --password-stdin "${API_REPO%%/*}"

# the task definitions run x86_64, so force the platform on arm machines
docker build --platform linux/amd64 -t "$API_REPO:latest" ../backend
# the worker image compiles the c++ engine, which lives outside backend/
docker build --platform linux/amd64 -t "$WORKER_REPO:latest" -f ../backend/Dockerfile.worker \
  --build-context engine=../engine ../backend

docker push "$API_REPO:latest"
docker push "$WORKER_REPO:latest"
```

### 4. Apply everything

```bash
terraform apply -var-file=environments/dev.tfvars
```

Takes roughly 10 to 15 minutes, almost all of it RDS and ElastiCache. When it finishes, `terraform output api_url` is the base URL of the api.

### 5. Run the database migrations

RDS has no public IP, so migrations run as a one-off task inside the VPC, reusing the api task definition with its command overridden:

```bash
aws ecs run-task \
  --cluster "$(terraform output -raw ecs_cluster_name)" \
  --task-definition "$(terraform output -raw api_task_definition_arn)" \
  --capacity-provider-strategy capacityProvider=FARGATE,weight=1 \
  --network-configuration "awsvpcConfiguration={subnets=[$(terraform output -json public_subnet_ids | jq -r 'join(",")')],securityGroups=[$(terraform output -raw api_security_group_id)],assignPublicIp=ENABLED}" \
  --overrides "{\"containerOverrides\":[{\"name\":\"$(terraform output -raw api_service_name)\",\"command\":[\"alembic\",\"upgrade\",\"head\"]}]}"
```

Its output lands in the api log group (step 7).

### 6. Smoke test

```bash
API_URL=$(terraform output -raw api_url)
curl "$API_URL/health"      # {"status":"ok"}
curl "$API_URL/health/db"   # {"status":"ok"} once the api can reach rds
```

The database is empty after every stand-up. To create a demo account with an analyzed portfolio (it goes through the api, so it needs no access to RDS):

```bash
cd ../backend
python -m scripts.seed --api-url "$API_URL"
cd ../infra
```

To point the local frontend at it:

```bash
cd ../frontend
VITE_API_URL=$API_URL npm run dev
```

`cors_origins` defaults to `http://localhost:5173`, which is what this needs.

### 7. Logs

```bash
aws logs tail "$(terraform output -json log_group_names | jq -r .api)" --follow
aws logs tail "$(terraform output -json log_group_names | jq -r .worker)" --follow
```

### 8. Tear it down

If CI deploys are on, set the `DEPLOY_ENABLED` repo variable back to `false` first, or the next push to `main` rebuilds the stack.

```bash
terraform destroy -var-file=environments/dev.tfvars
```

**This is the only real off switch.** The ALB and ElastiCache cannot be stopped, only deleted, and a stopped RDS instance restarts itself after 7 days. Destroy wipes the database, the bucket and the images, which is why the bucket, repositories and RDS are all configured to delete without protest.

Afterwards, confirm nothing billable is left:

```bash
terraform state list   # should print nothing
```

## Deploying a new image

With [CI/CD](#cicd) wired up, pushing to `main` does this for you. By hand: push a new tag (step 3 with a different tag), then:

```bash
terraform apply -var-file=environments/dev.tfvars -var image_tag=<tag>
```

If you re-push `latest` instead, the task definition does not change, so force a rollout:

```bash
aws ecs update-service --cluster "$(terraform output -raw ecs_cluster_name)" \
  --service "$(terraform output -raw api_service_name)" --force-new-deployment
```

## CI/CD

GitHub Actions authenticates to AWS through OIDC. There are no access keys stored in the repo, each run trades a short-lived GitHub token for one of the two roles from `ci/`:

| Role | Who can assume it | What it can do |
|---|---|---|
| `quantly-ci-plan` | workflow runs on a pull request | `ReadOnlyAccess`. A PR can run unreviewed code, so it can look but not touch. |
| `quantly-ci-deploy` | workflow runs on `main` | Apply the stack and push images. IAM is limited to roles named `quantly-*`. |

Wire the repo up once, under Settings > Secrets and variables > Actions > Variables (these are identifiers, not secrets):

| Variable | Value |
|---|---|
| `AWS_PLAN_ROLE_ARN` | `terraform -chdir=ci output -raw plan_role_arn` |
| `AWS_DEPLOY_ROLE_ARN` | `terraform -chdir=ci output -raw deploy_role_arn` |
| `TF_STATE_BUCKET` | `terraform -chdir=ci output -raw state_bucket` |
| `DEPLOY_ENABLED` | `true` only while a demo stack should exist, see below |

Until those are set, the AWS jobs skip themselves and everything else in CI still runs.

**On a pull request** that touches `infra/`, [`terraform-plan.yml`](../.github/workflows/terraform-plan.yml) checks formatting, validates all three roots, then runs `terraform plan` against the real state and posts the result as a PR comment. When the stack is torn down the plan simply shows everything as to-be-created.

**On a push to `main`**, [`deploy.yml`](../.github/workflows/deploy.yml) does the whole runbook below (steps 2 to 6) by itself:

1. creates the ECR repositories if they are missing
2. builds the api and worker images and pushes them tagged with the commit sha
3. `terraform apply -var image_tag=<sha>`, which rolls both services onto the new images
4. runs `alembic upgrade head` as a one-off task
5. waits for both services to settle, then hits `/health` and `/health/db`

It only runs while the repo variable `DEPLOY_ENABLED` is `true`. That variable is the demo switch: the stack bills by the hour, so a push should not quietly rebuild it after a teardown. Turn it on for a demo window (the first push, or a manual run from the Actions tab, then stands the whole stack up), and turn it off again **before** `terraform destroy`.

Pull requests also build both images without pushing them ([`images.yml`](../.github/workflows/images.yml)), so a broken Dockerfile is caught before it reaches `main`.

## Useful variables

All have defaults, see `variables.tf`. The ones worth knowing:

| Variable | Default | |
|---|---|---|
| `environment` | `dev` | Part of every resource name, so `dev` and `prod` can coexist. |
| `image_tag` | `latest` | Image tag both services deploy. |
| `certificate_arn` | `null` | ACM certificate. When set, the ALB serves HTTPS on 443 and redirects 80 to it. Point a CNAME at `alb_dns_name`. |
| `cors_origins` | `["http://localhost:5173"]` | Origins the api accepts browser requests from. |
| `google_client_id` | `""` | Enables Google sign-in on the api. |
| `worker_capacity_provider` | `FARGATE_SPOT` | Switch to `FARGATE` if Spot capacity is unavailable. |
| `api_cpu` / `api_memory` | `256` / `512` | |
| `worker_cpu` / `worker_memory` | `1024` / `2048` | |
| `enable_autoscaling` | `true` | Worker scaling on queue backlog, api scaling on request count and cpu. See below. |
| `worker_min_count` / `worker_max_count` | `0` / `5` | Bounds for the worker. At 0 an idle stack runs no workers. |
| `worker_backlog_target` | `20` | Queued jobs per running worker to hold. Derive it from `docs/capacity.md`, 20 is a placeholder. |
| `api_min_count` / `api_max_count` | `1` / `4` | |
| `api_requests_per_target` / `api_cpu_target` | `600` / `60` | Per-minute requests per api task and average cpu percent. |

## Autoscaling

`autoscaling.tf`, behind `enable_autoscaling`. It passes `terraform fmt` and `validate` but has not been planned against the real account or applied, so run `plan` before trusting it.

- A small Lambda (`lambda/queue_depth/handler.py`, stdlib plus boto3) runs every minute in the VPC. It reads `LLEN` of the celery queue from Redis db 1 and the running task count from `DescribeServices`, then publishes `Quantly/QueueDepth` and `Quantly/BacklogPerWorker` (depth divided by `max(running, 1)`).
- The worker service has a target tracking policy on `BacklogPerWorker` with target `worker_backlog_target`. `ecs-service` ignores `desired_count` changes once autoscaling owns it.
- The api service has two target tracking policies: ALB `RequestCountPerTarget` and average CPU. The higher desired count wins.
- Because the stack has no NAT gateway, the Lambda reaches ECS and CloudWatch through two interface VPC endpoints. They bill hourly per subnet, so turn autoscaling off (or tear the stack down) when not demoing.
- Scale from zero relies on the metric being defined at zero workers (hence the `max(running, 1)`) and on target tracking acting on it. If the plan or a test shows the worker staying at 0 with a backlog, set `worker_min_count = 1`.
- Replay a depth series through the same policy math with `loadtest/simulate_scaling.py`.

## Cost

Rough on-demand prices in `us-east-1`. Check the AWS pricing pages before relying on them.

| Resource | Approx. per month if left running |
|---|---|
| ALB | ~$16 + traffic |
| RDS `db.t4g.micro` + 20 GB | ~$14 |
| ElastiCache `cache.t4g.micro` | ~$12 |
| api task (0.25 vCPU / 0.5 GB) | ~$9 |
| worker task (1 vCPU / 2 GB, Spot) | ~$11 |
| Public IPv4 addresses (2 for the ALB, 1 per task) | ~$15 |
| S3, ECR, logs, SSM | cents |
| **Total** | **~$75** |

A NAT gateway would add ~$32/month per AZ on top, which is why there isn't one. Run for a two-hour demo and destroyed, the whole stack costs well under a dollar.
